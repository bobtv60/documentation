Heatmaps visualize player movement, events, and emotions as spatial data on your dashboard. They work with **every type of Roblox game** — static maps, procedurally generated worlds, instanced dungeons, teleportation games, and multi-place universes.

```lua
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Upview = require(ReplicatedStorage.Upview)

Upview:Init({
    ApiKey = "uv_live_abc123...",
    EnableHeatmaps = true,
}):Start()

local Heatmap = Upview:GetService("Heatmap")
```

## Quick Start

For most games, you only need **one line of code** beyond the initial setup:

```lua
-- Tell Upview which area the player is in
Heatmap:SetContext(player, "Lobby")
```

That's it. Everything else is automatic. Upview starts tracking positions, zones, deaths, and purchases the moment you call `Start()`.

## How It Works

When `EnableHeatmaps` is `true`, the HeatmapService runs a tracking loop every 2 seconds (configurable):

1. Reads each player's `HumanoidRootPart` position (server-side, cheat-proof)
2. Skips if the player hasn't moved more than 0.5 studs
3. Records the position with context, zone, and emotion metadata
4. Batches points and flushes them to the Upview backend automatically

<Note>
Position tracking uses the **server-side** character model. This means the data is accurate and cannot be spoofed by exploiters.
</Note>

## Contexts — The Key Concept

A **context** is a named space where coordinates make sense together. It's how Upview solves the "teleportation problem" that makes raw world coordinates useless in most Roblox games.

### Why Contexts Matter

Consider what happens without contexts:

- **Instanced dungeons**: 1,000 servers generate the same dungeon at different world positions. All heatmap points overlap into one meaningless blob.
- **Teleportation games**: Players teleport 50,000 studs away. The heatmap shows nothing useful at that scale.
- **Procedural worlds**: Every server has a different layout. Coordinates have no shared meaning.

With contexts, you tell Upview: "This player is in `Dungeon_Floor_3`." Now all data from every server's Floor 3 aggregates into one clean heatmap — regardless of where that floor is in world space.

### `Heatmap:SetContext(player, contextName, origin?)`

Sets the spatial context for a player. All subsequent position samples are grouped under this context name on the dashboard.

<ParamField path="player" type="Player" required>
  The target player.
</ParamField>

<ParamField path="contextName" type="string" required>
  A descriptive name for the area. Examples: `"Lobby"`, `"Dungeon_Floor_3"`, `"Shop_Interior"`, `"BossArena"`.
</ParamField>

<ParamField path="origin" type="BasePart | CFrame?">
  Optional reference point for coordinate conversion. When provided, player positions are recorded **relative to this origin**, so heatmaps align perfectly even when the same area spawns at different world positions across servers.
</ParamField>

```lua
-- ── Simple: Just group by name ──
-- Coordinates stay as world-space, but points are grouped by context
Heatmap:SetContext(player, "Lobby")

-- ── With origin: Coordinates become local to the reference point ──
-- Perfect for instanced areas or procedural rooms
local dungeonOrigin = workspace.Dungeon.SpawnPart
Heatmap:SetContext(player, "Dungeon_Floor_3", dungeonOrigin)

-- ── With CFrame: Full control over the reference frame ──
Heatmap:SetContext(player, "Arena", CFrame.new(1000, 0, 1000))
```

<Tip>
**When to use an origin**: If the same area can appear at different world positions across servers (instanced dungeons, procedural rooms, copied layouts), always pass an origin. Without one, points from different servers won't align on the heatmap.
</Tip>

### `Heatmap:ClearContext(player)`

Removes the context. Falls back to auto-anchoring or raw world coordinates.

```lua
Heatmap:ClearContext(player)
```

### `Heatmap:GetContext(player)`

Returns the player's current context name, or `nil`.

```lua
local ctx = Heatmap:GetContext(player)
```

## Common Game Patterns

### Static Map (Tycoon, Lobby, Obby)

No context needed — world coordinates work perfectly. Just enable heatmaps:

```lua
Upview:Init({
    ApiKey = "uv_live_abc123...",
    EnableHeatmaps = true,
}):Start()
-- Done. Positions are tracked automatically.
```

### Teleportation Game (Islands, Floors, Worlds)

Set the context when the player teleports:

```lua
-- Player teleports to an island
local islandPart = workspace.Islands[islandName].SpawnPoint
Heatmap:SetContext(player, islandName, islandPart)
```

### Instanced Dungeon / Procedural Room

Use the room's root part as the origin so all instances align:

```lua
-- Each server generates the dungeon differently, but the layout is the same
local dungeonRoot = workspace.GeneratedDungeon.RootPart
Heatmap:SetContext(player, "CaveDungeon", dungeonRoot)

-- When the player reaches floor 2
local floor2Root = workspace.GeneratedDungeon.Floor2.RootPart
Heatmap:SetContext(player, "CaveDungeon_Floor2", floor2Root)
```

### Multi-Place Universe

Set context in each Place's server script:

```lua
-- In Place "HubWorld" server script:
Heatmap:SetContext(player, "HubWorld")

-- In Place "BattleArena" server script:
Heatmap:SetContext(player, "BattleArena", workspace.ArenaCenter)
```

### Copied Room Layouts (Apartments, Shops)

Multiple physical rooms share one heatmap when they use the same context name:

```lua
-- 50 apartment instances, all called "StandardApartment"
-- Each has a different AnchorPart at its center
local apt = workspace.Apartments[playerAptId]
Heatmap:SetContext(player, "StandardApartment", apt.AnchorPart)
-- Dashboard shows one combined heatmap for all apartments
```

## Zero-Code Setup

If you prefer no code at all, use Roblox's **Tag Editor** in Studio.

### Anchors (Tag-Based Contexts)

<Steps>
  <Step title="Place a Part">
    Put a Part at the center of the area you want to track.
  </Step>
  <Step title="Tag it">
    Tag the Part with `UpviewAnchor` using the Tag Editor.
  </Step>
  <Step title="Set the context name">
    Add a string attribute called `UpviewContext` to the Part, e.g. `"CoffeeShopLayout"`.
  </Step>
</Steps>

When a player is within range (default 500 studs), their coordinates are recorded relative to the anchor's position. All rooms with the same `UpviewContext` value share one heatmap.

### Zones (Area Detection)

<Steps>
  <Step title="Place a Part">
    Size a Part to cover the area. Its bounding box defines the zone boundary.
  </Step>
  <Step title="Tag it">
    Tag the Part with `UpviewZone`.
  </Step>
  <Step title="Name it">
    Add a string attribute called `UpviewZoneName`, e.g. `"VIP_Lounge"`.
  </Step>
</Steps>

Zone enter/exit events are tracked automatically. Zone names appear as metadata on each position sample.

<Note>
**SetContext vs Anchors**: `SetContext()` is the recommended approach for most games. Tags are great for static maps where you want truly zero code. Both can coexist — `SetContext()` takes priority over auto-anchoring.
</Note>

## Emotions

Tag position data with player emotional state. Emotions show as coloured indicators on the dashboard.

### `Heatmap:SetPlayerEmotion(player, emotion)`

<ParamField path="player" type="Player" required>
  The target player.
</ParamField>

<ParamField path="emotion" type="string" required>
  One of: `"happy"`, `"frustrated"`, `"excited"`, `"calm"`, `"confused"`, `"bored"`, `"neutral"`.
</ParamField>

```lua
-- Player just lost a round
Heatmap:SetPlayerEmotion(player, "frustrated")

-- Player found a rare item
Heatmap:SetPlayerEmotion(player, "excited")

-- Reset after 30 seconds
task.delay(30, function()
    Heatmap:ClearPlayerEmotion(player)
end)
```

### `Heatmap:ClearPlayerEmotion(player)`

Removes the emotion. Subsequent samples will have no emotion tag.

### `Heatmap:GetPlayerEmotion(player)`

Returns the current emotion string or `nil`.

## Spatial Events

Record one-time events at a player's exact position. These show as distinct markers (diamonds, icons) on the dashboard — separate from the position density heatmap.

### `Heatmap:RecordEvent(player, eventType, eventData?)`

<ParamField path="player" type="Player" required>
  The target player.
</ParamField>

<ParamField path="eventType" type="string" required>
  The type of event. Use any string — common values include `"death"`, `"purchase"`, `"interaction"`, `"achievement"`, `"quest"`.
</ParamField>

<ParamField path="eventData" type="table?">
  Optional metadata table with additional context.
</ParamField>

```lua
-- Record a death with cause
Heatmap:RecordEvent(player, "death", {
    cause = "fall_damage",
    health = 0,
})

-- Record a purchase
Heatmap:RecordEvent(player, "purchase", {
    item = "legendary_sword",
    cost = 500,
    currency = "Coins",
})

-- Custom game event
Heatmap:RecordEvent(player, "BossDefeated", {
    bossName = "Dragon King",
    timeToKill = 47.5,
})
```

<Tip>
Deaths and purchases from Roblox's built-in systems (`Humanoid.Died`, `MarketplaceService`) are tracked automatically by default. You only need `RecordEvent()` for custom game events.
</Tip>

## Auto-Triggered Events

When `AutoTriggerEvents` is enabled (default: `true`), these events are recorded automatically:

| Roblox Event | Event Type | Data |
|---|---|---|
| `Humanoid.Died` | `"death"` | `cause` |
| `MarketplaceService.PromptProductPurchaseFinished` | `"purchase"` | `productId`, `source` |
| `MarketplaceService.PromptGamePassPurchaseFinished` | `"purchase"` | `gamePassId`, `source` |
| `Character.ChildAdded` (Tool) | `"interaction"` | `toolName` |
| `FeedbackService.OnFormCompleted` | `"interaction"` | `formSlug` |

## Zones API

### `Heatmap:GetCurrentZone(player)`

Returns the zone the player is currently inside, or `nil`.

```lua
local zone = Heatmap:GetCurrentZone(player)
if zone == "VIP_Lounge" then
    print(player.Name .. " is in the VIP lounge")
end
```

### Zone Change Signal

```lua
Heatmap.OnZoneChanged:Connect(function(player, newZone, oldZone)
    if newZone then
        print(player.Name .. " entered " .. newZone)
    end
end)
```

### Context Change Signal

```lua
Heatmap.OnContextChanged:Connect(function(player, newContext, oldContext)
    print(player.Name .. " moved from " .. (oldContext or "none") .. " to " .. (newContext or "none"))
end)
```

## Manual Anchoring (Legacy)

For code-based control using a physical `BasePart` reference:

### `Heatmap:SetPlayerAnchor(player, anchor?, context?)`

```lua
local shopPart = workspace.Shop.AnchorPart
Heatmap:SetPlayerAnchor(player, shopPart, "ShopLayout")

-- Clear the anchor
Heatmap:SetPlayerAnchor(player, nil)
```

<Note>
For most games, prefer `SetContext()` over `SetPlayerAnchor()`. `SetContext()` is simpler and supports CFrame origins in addition to parts.
</Note>

## Map Overlay

### `Heatmap:SetMapBounds(minPos, maxPos)`

Reports your map's bounding box so the dashboard can align your uploaded map image.

```lua
Upview:SetMapBounds(
    Vector3.new(-500, 0, -500),
    Vector3.new(500, 0, 500)
)
```

## `Heatmap:ForceFlush()`

Immediately sends buffered points to the backend. Normally the buffer auto-flushes at 50 points. This is useful before server shutdown or after recording critical events.

```lua
Heatmap:ForceFlush()
```

## Configuration

Pass these in `Upview:Init()`:

| Key | Type | Default | Description |
|---|---|---|---|
| `HeatmapTrackingInterval` | `number` | `2` | Seconds between position samples |
| `HeatmapMaxPointsPerFlush` | `number` | `50` | Buffer size before auto-flush |
| `HeatmapMinDistance` | `number` | `0.5` | Minimum studs moved to record a new point |
| `HeatmapAutoAnchorEnabled` | `boolean` | `true` | Use CollectionService tags for anchoring |
| `HeatmapAutoAnchorTag` | `string` | `"UpviewAnchor"` | Tag name for anchor parts |
| `HeatmapAutoAnchorDistance` | `number` | `500` | Max studs from anchor to activate |
| `HeatmapAutoZoneEnabled` | `boolean` | `true` | Use CollectionService tags for zone detection |
| `HeatmapAutoZoneTag` | `string` | `"UpviewZone"` | Tag name for zone parts |
| `HeatmapAutoTriggerEvents` | `boolean` | `true` | Auto-hook deaths, purchases, tool equips |

```lua
Upview:Init({
    ApiKey = "uv_live_abc123...",
    EnableHeatmaps = true,
    HeatmapTrackingInterval = 1.0,     -- Sample every second
    HeatmapMinDistance = 2.0,          -- Only record if moved 2+ studs
    HeatmapAutoTriggerEvents = true,   -- Track deaths/purchases automatically
}):Start()
```

<Warning>
Setting `HeatmapTrackingInterval` below 1 second increases data volume significantly. For most games, 2 seconds provides good coverage without excessive data.
</Warning>

## Signals

| Signal | Parameters | Description |
|---|---|---|
| `OnPointsCollected` | `{SpatialPoint}` | Fired when a batch of points is flushed |
| `OnZoneChanged` | `Player, string?, string?` | Fired when a player enters or exits a zone |
| `OnEmotionChanged` | `Player, string` | Fired when a player's emotion is set |
| `OnContextChanged` | `Player, string?, string?` | Fired when a player's context changes |
